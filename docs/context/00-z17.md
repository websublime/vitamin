## Understanding
- Outcome: the HTMX persona (PRD §1, Persona 2) gets a tested guarantee that line components work with htmx
  through the native paths. Those paths are host-level `hx-*`, slotted light-DOM `hx-*`, a form-associated
  value inside an htmx form, and a component event as `hx-trigger`. H1 showed that all of them work without an
  adapter on htmx 2.0.11 and 4.0.0 in chromium, firefox and webkit.
- Stated by Miguel (row `Z17`, retrospective):
  - A component-spec-template rule, next to C1–C8, makes a compound component name the commit event that
    consumers use as `hx-trigger`.
  - The Playwright tier of every value-bearing or compound component gains an htmx check. It covers a value
    inside `<form hx-post>`, `hx-trigger` on the commit event, and content swapped into slots.
  - A Storybook HTMX guide.
  - The design targets htmx 4. The checks run on htmx 2 and htmx 4 while upstream supports 2.x.
  - `LineHtmxElement` is deferred as a nice-to-have after 1.0, and `__experimental__/htmx/` stays as a
    reference.
- Orchestrator defaults, accepted with the recommendations:
  - The work runs now on the Phase 00 ledger, so row `Z17` does not move to a Phase 1 ledger.
  - The checks reuse the exact root devDependencies `htmx2` (2.0.11) and `htmx4` (4.0.0). The Phase 1
    dependency refresh owns any version bump.
  - Playwright `page.route` answers the htmx requests, so the tier needs no extra web server.
  - The `hx-trigger` check also proves that a non-commit interaction inside a compound host sends no request,
    because H1 `hostNative` showed that a host-level `click` trigger fires for every click inside the shadow
    root.
  - The shared harness lives in `packages/line-core/__tests__/integration/htmx/`. The Vite integration server
    already serves that root, and the retrospective's revisit condition 8 names the path.
  - Branch `feat/00-z17-htmx-native-support`.

## Understanding
- Outcome: no workflow saves or restores the `bun` executable in the Actions cache, so no job runs a `bun`
  binary that another job saved.
- Stated:
  - R2 says the build jobs run third-party build code on `main` with the default `setup-bun` cache, and
    `release.yml` restores the same cache in a job with `contents: write` and `id-token: write`.
  - R2 suggests `no-cache: true` in `release.yml` and the snapshot workflows.
- Observed on `0577781`:
  - `setup-bun` v2.2.0 (`0c5077e`) caches only `~/.bun/bin/bun`, under the key `bun-<sha1(download URL)>`. It
    restores the entry in the main step and saves it in the post step at job end, only on a cache miss. After
    a restore it checks only that `bun --revision` prints the expected version.
  - Six `setup-bun` steps keep the default cache. They sit in `checks.yml`, `release.yml`,
    `snapshot-version.yml`, `snapshot-deploy.yml` and the build jobs of `deploy-site.yml` and
    `deploy-storybook.yml`. The two deploy jobs already set `no-cache: true`. The eight §6.F.5 `setup-bun`
    steps match the workflows.
  - The `main` cache entry `bun-+NUKu9E/U4apAe78eSCZvQ/GSdc=` (Bun 1.4.3, 41 001 435 bytes) was saved at
    2026-10-13T13:11:07Z by the `deploy-storybook.yml` build job (run 38402867422). Its post step ran after the
    packages and Storybook build. The `release.yml` and `deploy-site.yml` runs of the same push downloaded Bun
    and failed to reserve the key.
  - `release.yml` run 38514415655 (2026-10-14, the `00-Z28` merge) logged
    `Using a cached version of Bun: 1.4.3+c6da4a4d3`.
  - In `deploy-site.yml` run 38514415658, `setup-bun` took 1 s with `no-cache: true` and 2 s with the cache.
  - The repository uses no other Actions cache. `setup-node` runs with `package-manager-cache: false`, and no
    workflow uses `actions/cache`.
  - Caches saved on `main` are readable from every branch and pull request. Caches saved on a pull-request ref
    are not readable from `main`.
- Assumed:
  - The logs show the path exists, not that it was abused.
  - A compromised build dependency in a build job on `main` can replace `~/.bun/bin/bun` before the post step
    saves it, whenever the key misses (a `.bun-version` bump or a 7-day eviction).

## Decisions

| Fork | Decision | Rejected |
|---|---|---|
| Scope | `no-cache: true` in all six `setup-bun` steps that still cache, so no workflow saves or restores the Bun executable (Miguel, 2026-10-14) | The three release-path jobs only |
| Step shape (orchestrator default) | Each step keeps its flow mapping and gains the input, `with: { bun-version-file: .bun-version, no-cache: true }`, the form the two deploy jobs use. Each changed step carries an `AM-069` comment | — |
| Existing cache entries (orchestrator default) | After merge, the orchestrator deletes every `bun-*` Actions cache entry with `gh cache delete`, on every ref. No workflow restores them after the merge, and the entries would otherwise linger until the 7-day eviction | Deleting before merge, because pushes to `main` under the old workflows would save them again |

## Understanding
- Outcome: `bun.lock` stops drifting from the workspace manifests after a Version PR, and the publisher keeps
  shipping correct internal ranges.
- Stated:
  - AM-036 rejected syncing `bun.lock` after versioning because, on Bun 1.3.14, it needed text surgery on the
    lockfile and a `version:` hook in `release.yml`.
  - Miguel asked to re-evaluate syncing with `bun install` instead of the staging.
- Observed on `a5e86a8`:
  - `bun.lock` records line-colors 0.1.2, line-core 0.1.0 and line-tokens 0.1.2 while the manifests say 0.1.3,
    0.1.1 and 0.1.3. Version PR #254 (`f14dcb6`) left `bun.lock` alone. A plain `bun install` rewrites those three
    entries (AM-071 probes), so any local plain install on `main` leaves a `bun.lock` diff.
  - `release.yml` runs `changesets/action` v1.9.0 (`a45c4d5`) with no `version:` input, so the action runs
    `@changesets/cli` `version` directly. With a `version:` input it runs that command instead, and it commits every
    working-tree change into the Version PR, emulating `git add .` (`src/run.ts` `runVersion`, `src/git.ts`
    `pushChanges`).
  - The release job holds `contents: write` and `id-token: write`, and installs with `--ignore-scripts`
    (AM-067).
  - `snapshot-version.yml` and `snapshot-deploy.yml` run `bun run snapshot:version` after a frozen install and
    never commit. The snapshot versions exist only in the working tree.
  - `scripts/verify-pack.mjs` `stageAndPack` copies each package, rewrites `workspace:` ranges from
    `packages/*/package.json`, and packs the copy. Guard (d) fails a leftover `workspace:` range. Guard (e) fails an
    internal range that the workspace version does not satisfy. Guard (e) does not catch a lagging floor, because
    `^0.1.0` is satisfied by 0.1.1.
- Verified in the review gate (was assumed in understand):
  - A `bun install --ignore-scripts` after `changeset version` changes only the workspace version entries in
    `bun.lock`. Two independent clean-copy probes on Bun 1.4.3 (the supervisor lens and the reviewer lens) showed
    exactly the three stale entries on `main`, then exactly the bumped package after a throwaway Version run.

## Decisions

| Fork | Decision | Rejected |
|---|---|---|
| Shape | Sync `bun.lock` in the Version PR and keep the staging (Miguel, 2026-10-19) | Keep the staging only; sync `bun.lock` and pack in place without the staging |
| Version command (orchestrator default) | The root `version` script becomes `changeset version && bun install --ignore-scripts`, and the `release.yml` `changesets/action` step gains `version: bun run version`. `--ignore-scripts` keeps lifecycle scripts out of the job that holds `contents: write` and `id-token: write` (AM-067) | — |
| Current drift (orchestrator default) | The branch commits a resynced `bun.lock`, produced by `bun install --ignore-scripts` on the branch | Waiting for the next Version PR to resync |
| Snapshot path (orchestrator default) | Unchanged. Snapshot versions live only in the job's working tree and are never committed, so the staging keeps covering them | — |

## Acceptance criteria
- The root `version` script and the `release.yml` `version:` input are as decided, and the §6.F.5 blocks and the
  publish path text match them after AM-072.
- `bun.lock` on the branch matches every workspace manifest, a plain `bun install` leaves no diff, and
  `bun install --frozen-lockfile` exits 0.

- `verify-pack` and `publish.mjs --dry-run` still pass, and `actionlint` passes on `release.yml`.
- After merge, the next Version PR carries the `bun.lock` change.
